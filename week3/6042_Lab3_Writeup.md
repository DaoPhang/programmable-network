# Lab 3: Inside the Forwarding Path

**Student ID suffix:** 6042  
**Address blocks:** `10.42.0.0/16` and `fd00:6042::/32`

This lab used three Linux routers and three hosts to investigate static routing, longest-prefix matching, route fallback, unreachable destinations, routing loops, and IPv6 forwarding. Initially, h1 could reach its gateway at `10.42.1.1` with 0% packet loss, but could not reach h2. The routers had only directly connected routes, and IPv4 forwarding was disabled. After enabling forwarding, r1 returned `Destination Net Unreachable` until the required static routes were added.

## 1. Why did h2 and h3 take different paths despite both belonging to 10.42.32.0/20?

The destinations took different paths because r1 applied **longest-prefix matching**. Its routing table contained two overlapping routes:

| Prefix | Next hop | Router |
|---|---|---|
| `10.42.32.0/24` | `10.42.12.2` | r2 |
| `10.42.32.0/20` | `10.42.13.2` | r3 |

The address of h2, `10.42.32.10`, matched both routes. The `/24` was more specific, so r1 forwarded directly to r2. The address of h3, `10.42.33.10`, matched only the `/20`, so r1 forwarded through r3.

The route lookups confirmed these decisions (relevant fields shown):

```text
10.42.32.10 via 10.42.12.2 dev r1-eth1
10.42.33.10 via 10.42.13.2 dev r1-eth2
10.42.40.1 via 10.42.13.2 dev r1-eth2
```

Traceroute showed the resulting paths (hop addresses shown):

```text
To h2:
1  10.42.1.1
2  10.42.12.2
3  10.42.32.10

To h3:
1  10.42.1.1
2  10.42.13.2
3  10.42.12.2
4  10.42.33.10
```

Therefore, h2 followed **h1  r1  r2  h2**, while h3 followed **h1  r1  r3  r2  h3**.

## 2. What changed after deleting r1's /24 route, and why did h2 remain reachable?

After deleting `10.42.32.0/24`, r1 no longer had the specific route directly towards r2. However, h2 still matched the remaining `10.42.32.0/20` route through r3.

The new trace was (hop addresses shown):

```text
1  10.42.1.1
2  10.42.13.2
3  10.42.12.2
4  10.42.32.10
```

The path increased from three to four hops. h2 remained reachable because r3 still had a route towards r2, and the routers had the necessary return routes towards h1. This demonstrated fallback to a less specific matching route.

When r3's `/20` route was subsequently deleted, the trace stopped at r3:

```text
1  10.42.1.1  0.110 ms  0.102 ms  0.101 ms
2  10.42.13.2  0.100 ms !N  0.090 ms !N  0.087 ms !N
```

The `!N` indicated **network unreachable**: r3 could no longer forward towards h2's network.

## 3. Why did IPv4 hop 3 towards h3 show r2's r1-r2 address? How did IPv6 differ?

Although the forward probe reached r2 through its link with r3, the IPv4 traceroute displayed `10.42.12.2`, r2's address on the link towards r1.

The ICMP reply generated by r2 was routed back towards h1 through r1. In this experiment, the reply used the address of that outgoing interface. Consequently, the displayed address reflected the reply's return direction rather than the interface where the original probe arrived. The forward and return paths were therefore asymmetric.

The IPv6 trace showed:

```text
1  fd00:6042:1::1  0.166 ms  0.177 ms  0.210 ms
2  fd00:6042:13::2  0.240 ms  0.247 ms  0.252 ms
3  fd00:6042:23::2  0.256 ms  0.296 ms  0.329 ms
4  fd00:6042:33::10  0.371 ms  0.372 ms  0.387 ms
```

At hop 3, `fd00:6042:23::2` identified r2's interface on the **r3-r2 link**. This address was more useful for understanding the forward path because it identified the interface through which the probe reached r2.

## 4. How did the routing loop occur, and what stopped it?

The loop formed after r1's `/24` route had been removed and r3's `/20` route was configured to point back towards r1.

For traffic to h2:

- r1's `/20` route forwarded the packet to r3 at `10.42.13.2`.
- r3's `/20` route forwarded it back to r1 at `10.42.13.1`.
- Both routers repeatedly applied these same decisions.

Traceroute demonstrated the alternating routers (hop addresses shown):

```text
1  10.42.1.1
2  10.42.13.2
3  10.42.1.1
4  10.42.13.2
5  10.42.1.1
6  10.42.13.2
7  10.42.1.1
8  10.42.13.2
```

Ping also reported:

```text
From 10.42.13.2 icmp_seq=1 Time to live exceeded
From 10.42.13.2 icmp_seq=2 Time to live exceeded
```

Each forwarding hop reduced the packet's **Time to Live (TTL)**. When TTL expired, the router discarded the packet and generated an ICMP Time Exceeded message. TTL prevented individual packets from circulating indefinitely, although the incorrect routes remained configured.

## 5. Why does TCAM use ternary matching, and what limits route capacity?

A routing prefix specifies fixed address bits followed by bits that can have any value. TCAM supports three matching states: **0, 1, and "don't care."** The wildcard state allows one entry to match every destination within a prefix.

For example, a `/24` fixes the first 24 bits, while the remaining eight bits are wildcards. A `/20` fixes fewer bits and therefore matches a larger address range. When multiple entries match, the lookup must prioritise the entry with the longest prefix, reproducing the decision observed for h2.

Route capacity is limited by the hardware's finite table resources. The number of available TCAM entries, entry width, and allocation of resources to other functions affect how many routes can be stored. Wider entries, such as those needed for IPv6 on some hardware, can consume more resources. Therefore, forwarding-table capacity depends on the router's hardware design and configuration.
